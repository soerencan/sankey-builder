# Sankey Builder

Build Sankey diagrams in the browser. Edit nodes and links, choose colors and alignment, and see the diagram update as you work.

The app saves your work in the current browser and supports System, Light, and Dark themes.

[Open Sankey Builder](https://soerencan.github.io/sankey-builder/)

## Development

Use the Bun version in [`.bun-version`](.bun-version) and the Node version in [`.nvmrc`](.nvmrc). Bun runs the development server and build; Node runs Vitest and TypeScript. If you use nvm, run `nvm use` to select Node.

### Dev server

```sh
bun install
make dev
```

Open the URL printed by the development server. Bun bundles TypeScript and reloads changes during development.

### Preview the production build

```sh
make build
python3 -m http.server 8000 --directory dist
```

Open [localhost:8000](http://localhost:8000) to preview the built site, including its license notices. Opening `index.html` directly with `file://` is unsupported because browsers block its ES module imports.

The footer's Third-party licenses link works in the built site; the page is not generated by `make dev`.

### Checks

| Command | Purpose |
| --- | --- |
| `make lint` | Check formatting and lint rules with Biome |
| `make format` | Apply Biome formatting and lint fixes |
| `make typecheck` | Check TypeScript without emitting files |
| `make test` | Run Vitest tests, including the production build smoke tests |
| `make test-unit` | Run tests without the production build smoke tests |
| `make test-dist` | Build and test the production output |

Unit tests sit beside their modules in `src/` and `scripts/`. Integration tests in `tests/integration/` start the app against the real HTML, D3, and SortableJS using happy-dom, a simulated browser environment. The build tests in `tests/build/dist.test.ts` build the site, check relative asset URLs and license notices, and boot the emitted bundle.

For manual browser checks, see [VERIFICATION.md](VERIFICATION.md).

### Browser tests

Playwright tests the production build, covering keyboard navigation, mouse dragging, file upload/download, and SVG/PNG rendering. Browser errors, warnings, and failed requests fail the tests.

Install the browser binaries once, then run the interaction and export tests:

```sh
bunx playwright install chromium webkit
make test-browser
```

Screenshot comparisons and updates require Docker Compose and run in a pinned Linux container for consistent rendering.

| Command | Purpose | Docker required |
| --- | --- | --- |
| `make test-browser` | Build and run interaction and export tests in Chromium and WebKit | No |
| `make test-browser-ui` | Build and open the interactive runner for those tests | No |
| `make test-browser-ci` | Run the full browser suite, including screenshots, against existing `dist/` | Yes |
| `make test-browser-snapshots` | Build and update screenshot baselines | Yes |

`make test-browser` and `make test-browser-ui` build before starting so the tests run against the current code.

### Continuous integration and deployment

GitHub Actions runs lint, type checks, tests, and a production build on pull requests and pushes to `main`. The build job runs Playwright in the pinned Linux container against the same output it uploads to GitHub Pages. Pushes to `main` deploy automatically after those checks pass. See [the CI workflow](.github/workflows/ci.yml) for details.

### Screenshot review and updates

Visual tests compare new screenshots with committed baselines to detect appearance changes. `make test-browser-snapshots` generates the baseline PNGs in [`tests/browser/visual.spec.ts-snapshots/`](tests/browser/visual.spec.ts-snapshots/). Reviewing and committing those images establishes the expected appearance.

A mismatch fails the test. The Playwright report shows the expected image, the actual image, and their difference.

For a CI failure, download `browser-test-report` from the Actions run's Artifacts, extract it, and run `bunx playwright show-report /path/to/extracted/playwright-report`. Reports also include failure traces. CI uploads reports only on failure and retains them for seven days.

To reproduce a failure locally, start Docker, build the app, run the full browser suite, and open its report:

```sh
make build && make test-browser-ci
bunx playwright show-report
```

For an unintended change, fix the code and rerun the tests. To accept an intentional change:

1. Run `make test-browser-snapshots`.
2. Inspect the changed PNGs.
3. Run `make test-browser-ci` against the updated baselines, then commit them with the code.

Keep the Playwright image in [`compose.yaml`](compose.yaml) at the same version as `@playwright/test`, updating both its tag and digest. Browser upgrades can change rendering and require baseline review.

## Codebase

| Location | Responsibility |
| --- | --- |
| [`src/app/`](src/app/) | App startup, state changes, notices, and page composition |
| [`src/model/`](src/model/) | Graph edits, settings, validation, and data normalization |
| [`src/features/editor/`](src/features/editor/) | Node and link editing, value drafts, and row reordering |
| [`src/features/diagram/`](src/features/diagram/) | Layout, SVG rendering, preview sizing, and image conversion |
| [`src/features/settings/`](src/features/settings/) | Setting controls, palettes, and theme application |
| [`src/features/files/`](src/features/files/) | JSON import/export and browser downloads |
| [`src/platform/`](src/platform/) | Browser storage |
| [`src/shared/`](src/shared/) | Shared controls, dialogs, icons, and notices |

The `diagram` and `editor` features stay independent: neither imports from the other. Both may use `settings` and `files` for shared functionality.

Editing state is separate from the displayed diagram so users can keep incomplete or invalid work. The preview and image exports show the last valid diagram.
